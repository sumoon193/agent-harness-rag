# 测试与质量门禁开发规范

本模块规定项目的测试分层、质量门禁和验收命令。它不是独立业务模块，而是所有模块都必须遵守的开发纪律。

## 测试分层

1. **Unit tests**：纯函数、schema、状态机、chunker、RRF、ACL、tool registry。
2. **Service tests**：使用 fake adapter 测试 ingestion、retrieval、agent run、approval、eval。
3. **API tests**：测试 FastAPI request / response、错误码、SSE。
4. **Integration tests**：连接 PostgreSQL、Redis、Milvus、Elasticsearch、MinIO。
5. **E2E tests**：从上传文档到 Agent Run 审批完成。
6. **Frontend tests**：组件、交互和关键页面状态。

## 默认测试原则

- 单元测试不依赖 Docker。
- 单元测试不依赖云 API key。
- LLM、embedding、reranker、vector store、BM25、Phoenix 都必须有 fake adapter。
- 每个 bugfix 必须先有失败测试。
- 每个模块至少覆盖一个成功路径和一个失败路径。

## 推荐命令

```powershell
python -m pytest tests/unit -v
python -m pytest tests/service -v
python -m pytest tests/api -v
python -m pytest tests/integration -v
npm test
npm run build
```

integration 和 e2e 可以依赖 Docker；unit 和 service 不允许依赖 Docker。

## 质量门禁

进入下一阶段前必须满足：

- 当前阶段单元测试通过。
- 核心失败路径有测试。
- 新增 public schema 有序列化测试。
- 新增 API 有 request / response 测试。
- 新增 adapter 有 fake 和真实集成边界说明。
- 文档同步更新。

## 测试数据

标准 HR 样例至少包含：

- 入职制度。
- 试用期转正制度。
- 报销制度。
- 请假制度。
- 一份无权限文档。
- 一份含制度编号的文档，如 `HR-2026-04`。

## 不做什么

- 不用真实云模型输出作为单元测试断言。
- 不把“手动跑过 demo”当作测试。
- 不跳过失败路径。
- 不把 integration test 混进默认快速测试。

## 验收标准

- 开发者能用一条命令运行快速测试。
- 每个模块规范里的测试都能映射到具体测试文件。
- CI 或本地脚本能区分 fast、integration、e2e。
