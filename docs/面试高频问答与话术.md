# EnterpriseMind Agent Harness RAG 高频面试问答与话术

本文用于面试前快速背诵和模拟问答。回答时建议采用固定结构：

```text
先一句话结论 -> 再讲项目里的实现 -> 最后落到工程价值或风险控制
```

## 0. 一分钟项目介绍

**问题：请你简单介绍一下这个项目。**

**话术：**

EnterpriseMind Agent Harness RAG 是一个面向企业内部制度流程的知识任务智能体平台，V1 聚焦 HR 入职、转正、报销、请假等制度问答和模拟工单办理。

它不是普通的“检索后生成答案”的 RAG Chatbot，而是把系统拆成两层：RAG 作为可信证据层，负责文档入库、解析、分块、混合检索、重排、引用和评测；Agent Harness 作为智能体执行治理层，负责 Agent Run 生命周期、计划生成、工具注册、人工审批、checkpoint/resume、权限控制、审计日志和 trace。

标准 Demo 是用户问“新员工入职到转正要办哪些事项”，系统检索 HR 制度 evidence，生成办理 checklist 和 plan，准备调用 `create_mock_hr_ticket`，因为这是写入型工具，所以 Harness 会暂停等待用户审批。用户 Approve 后，系统从 checkpoint 恢复，返回 mock ticket result、citations 和 trace。

**重点落点：**

- 不是普通 RAG，而是 Agent Harness + RAG。
- 有 citations、ACL、审批、恢复、trace、eval。
- 体现的是企业级 Agent 可控执行能力。

## 1. 项目定位与价值

### 1.1 为什么说它不是普通 RAG Chatbot？

**话术：**

普通 RAG 主要解决“根据文档回答问题”，核心链路通常是检索、拼 prompt、生成答案。而这个项目把 RAG 定位成可信证据层，只负责提供可追溯 evidence 和 citations；真正的亮点是上层 Agent Harness，它把一次用户请求建模成完整的 `AgentRun`，管理计划、工具调用、审批、恢复、审计和 trace。

所以这个系统不只回答“制度是什么”，还可以基于制度证据生成办理计划，并在人工审批后执行模拟 HR 工单。这也是它和普通知识库问答最大的区别。

### 1.2 这个项目解决了什么企业问题？

**话术：**

企业内部常见问题有三个：知识分散，员工不知道制度在哪里；回答不可追溯，无法确认答案依据；智能体如果直接执行工具，风险不可控。

这个项目分别对应解决：用 RAG evidence/citations 提供可信来源；用 ACL 和低置信度拒答控制答案边界；用 Agent Harness 的审批、checkpoint/resume 和审计日志控制工具执行风险。V1 选 HR 场景，是因为 HR 制度天然包含流程、角色、审批和权限，适合展示完整闭环。

### 1.3 你这个项目最核心的亮点是什么？

**话术：**

我会重点讲三个亮点。

第一是可信证据层：检索结果不是简单文本片段，而是结构化 `EvidenceBundle`，包含来源、章节、分数、ACL metadata 和 citation。

第二是 Agent Harness：所有写入型工具都必须审批，审批前不会执行，审批后可以从同一个 run/thread 的 checkpoint 恢复，避免重复执行前面的检索和计划。

第三是工程闭环：项目有 fallback mode 和 full mode，单元测试使用 deterministic fake，不依赖 Docker 和云 API；full mode 再接 PostgreSQL、Redis、Milvus、Elasticsearch、MinIO、Celery、Qwen 和 Phoenix。

### 1.4 为什么 V1 选择 HR 场景？

**话术：**

HR 制度流程非常适合做 Agent Harness + RAG 的 Demo。它既有制度文本和引用依据，也有流程步骤，比如入职、转正、请假、报销；同时又有写入动作，比如创建工单，这些动作必须审批。

所以 HR 场景可以同时展示 RAG 的 evidence/citation，也能展示 Agent 的 plan、approval、tool result 和 trace。如果一开始选过大的企业全场景，反而会模糊主线。

### 1.5 V1 不做 GraphRAG / MCP 的原因是什么？

**话术：**

这是一个范围控制问题。V1 的目标是先跑通 Agent Harness + RAG 的主链路，包括文档入库、检索、引用、审批、恢复、前端控制台和测试闭环。

GraphRAG / LightRAG 适合处理跨文档、多实体、多跳关系推理，MCP 适合把能力标准化暴露给外部 Agent。这些很有价值，但不是 V1 主链路的必要条件。为了保证项目完成度，我把它们冻结为 V2 非目标，只保留设计边界。

## 2. 总体架构

### 2.1 系统整体架构怎么分层？

**话术：**

整体可以分成五层。

第一层是 API 层，FastAPI 负责协议适配，比如 documents、ingestions、agent-runs、approvals、eval、health。

第二层是领域服务层，包括 ingestion、parser、chunker、retrieval、answer、agent、graph、security、observability。

第三层是 RAG 证据层，负责解析、分块、embedding、BM25、RRF、rerank 和 EvidenceBundle。

第四层是 Agent Harness 治理层，负责 run 状态机、工具注册、审批、恢复和审计。

第五层是外部适配层，full mode 接 PostgreSQL、Redis、Milvus、Elasticsearch、MinIO、Qwen、Celery、Phoenix；fallback mode 用 in-memory 和 fake 保证开发测试稳定。

### 2.2 为什么要设计 fallback mode 和 full mode？

**话术：**

主要是为了工程可控性。RAG/Agent 项目如果一开始就依赖 Docker、中间件、云模型和网络，很容易被环境问题拖住，单元测试也会不稳定。

所以我先实现 pure Python / in-memory / deterministic fake 的 fallback 主链路，保证核心领域逻辑可测、可跑、可演示。之后再把存储、检索、队列、模型等替换成真实 adapter。这样既能保证开发效率，也能体现生产扩展方向。

### 2.3 API 层为什么不能写领域决策？

**话术：**

API 层只应该做请求解析、依赖注入、调用 service 和格式化响应。如果把审批规则、ACL 规则、检索策略写在 API 层，后续 CLI、Celery worker、LangGraph 节点或者测试调用同一逻辑时就会重复实现，容易出现行为不一致。

所以项目里把领域决策放在 service 层，例如 `approval_manager`、`permission_filter`、`hybrid_retriever`、`grounded_answer`。API 层只是编排入口。

### 2.4 你用了哪些 Adapter / Fake？

**话术：**

外部依赖基本都通过 Protocol 或 adapter 隔离。比如 storage 有 `LocalFileStorage` 和 `MinIOStorage`；检索有 in-memory vector store、memory BM25、Milvus adapter 和 Elasticsearch BM25 adapter；embedding/rerank 有 mock adapter 和 Qwen adapter；rate limit 有 in-memory 和 Redis 版本；trace 有 fallback log exporter 和 Phoenix/OTel exporter。

这样做的好处是单元测试用 deterministic fake，full mode 再接真实服务，不会让业务逻辑和外部系统强耦合。

## 3. RAG 证据层

### 3.1 文档从上传到可检索经历了哪些步骤？

**话术：**

主链路是：上传文档，创建 ingestion task，保存原始 payload，然后 parser 解析 Markdown 或 Plain Text，生成结构化 block；接着通过 structural、semantic 或 hybrid chunker 分块；再生成 context prefix、embedding 和 BM25 索引；最后写入 vector store / sparse store，并更新 ingestion 状态为 ready。

full mode 可以通过 Celery 异步入库，fallback mode 默认同步执行，保证 Demo 和测试稳定。

### 3.2 为什么要做 hybrid chunking？

**话术：**

固定长度切分很容易把制度条款、表格或流程步骤切断，导致检索命中后上下文不完整。我的思路是先用 structural chunking 按标题、章节、列表等结构切出边界，再用 semantic chunking 在语义完整的位置细分，最后通过 hybrid chunking 组合两者。

这样既能保留制度文档的结构，也能控制 chunk 粒度，后续 citation 能定位到章节或段落。

### 3.3 Dense + BM25 混合检索解决什么问题？

**话术：**

Dense 向量检索适合语义问题，比如“转正流程怎么走”；BM25 适合精确关键词、制度编号、条款号，比如“HR-2026-04 第 12 条”。企业制度问答里这两类 query 都很常见，所以单独用一种检索都不够稳。

项目里先分别召回 dense 和 sparse 结果，再用 RRF 融合排序，最后用 reranker 对 top-N 候选精排，构造 EvidenceBundle。

### 3.4 RRF 是什么？为什么用它？

**话术：**

RRF 是 Reciprocal Rank Fusion，它不直接比较不同检索器的原始分数，而是根据排名位置做融合。这样可以避免 dense similarity 和 BM25 score 量纲不同的问题。

在项目里，Milvus 和 Elasticsearch 的分数不可直接比较，用 RRF 可以比较稳定地把多个召回源合并，再交给 reranker 精排。

### 3.5 EvidenceBundle 里有什么？

**话术：**

EvidenceBundle 不是简单文本列表，而是结构化证据集合。每条 evidence 包含 chunk 内容、来源文档、章节路径、页码或段落信息、检索分数、rerank 分数、ACL metadata 和 citation 所需信息。

这样 answer service、Agent plan、tool approval 和 eval 都能基于同一份证据结构工作，而不是各自解析原始文本。

### 3.6 为什么用户可见答案必须有 citation？

**话术：**

企业制度问答不能只追求“看起来像正确答案”，必须能追溯到制度来源。citation 可以让用户知道答案依据来自哪份文档、哪个章节，也方便后续审计和评测。

项目里要求关键结论必须能关联到 citation；如果证据不足、冲突或置信度低，就拒答或追问，而不是让模型自由发挥。

### 3.7 如果检索不到证据怎么办？

**话术：**

系统不会硬答。低置信度处理模块会判断 evidence 是否不足，如果不足，会返回拒答或追问，例如提示用户补充部门、岗位、制度范围等信息。

这体现的是 grounded answer 的约束：宁可少答，也不编造没有依据的企业制度。

## 4. Agent Harness 与审批恢复

### 4.1 Agent Harness 是什么？

**话术：**

Agent Harness 可以理解为智能体执行治理层。它不是某一个 LLM prompt，而是一套围绕 Agent Run 的运行时机制，负责状态机、步骤记录、工具注册、权限控制、人工审批、checkpoint/resume、审计和 trace。

在企业场景里，Agent 最大风险不是只答错，而是错误执行有副作用的动作。所以 Harness 的核心价值是让 Agent 可暂停、可审批、可恢复、可审计。

### 4.2 Agent Run 生命周期怎么设计？

**话术：**

一次用户请求会创建一个 `AgentRun`，状态大致包括 created、running、retrieving_evidence、planning、awaiting_approval、resumed、completed、failed、cancelled。

每个阶段都会通过 step logger 记录输入、输出、状态、证据、工具调用、审批结果和错误信息。这样一次 Agent 执行不是黑盒，而是一条可回放的工作流。

### 4.3 为什么写入型工具必须审批？

**话术：**

因为写入型工具会产生副作用，比如创建工单、发送邮件、修改数据。企业 Agent 不能只靠模型自己判断是否执行，否则一旦模型误判或受到 prompt injection 影响，就可能造成真实业务风险。

所以项目里工具有 risk level 和 `requires_approval`。像 `policy_search` 是只读工具，可以自动执行；`create_mock_hr_ticket` 是写入型工具，审批前只生成 tool call preview，绝不执行。

### 4.4 审批前如何保证工具没有执行？

**话术：**

工具执行前会经过 Tool Executor 和 Approval Manager。对于 `requires_approval=true` 的工具，系统只创建 approval request 和 tool call 记录，把 run 状态切到 `awaiting_approval`，不会调用工具实现函数。

只有用户 Approve 后，审批决策写入 run 和 audit step，系统才从 checkpoint resume，继续执行对应工具。这个机制是 Harness 和普通 function calling 的关键区别。

### 4.5 Approve / Edit / Reject 怎么处理？

**话术：**

Approve 表示按原参数继续执行工具；Edit 表示用户修改工具参数后再执行；Reject 表示拒绝该写入动作，Agent 会记录拒绝原因并停止或重新规划。

无论哪种决策，都会写入 approval 记录、Agent Step 和 trace，保证后续能审计“谁在什么时候批准或拒绝了什么动作”。

### 4.6 checkpoint/resume 怎么避免重复执行？

**话术：**

审批中断时，前面的检索、证据、计划、tool call preview 都已经记录在 run state 或 LangGraph thread checkpoint 里。用户批准后，系统用同一个 run id / thread id 恢复，而不是重新创建一次 run。

这样可以避免重复检索、重复计划，更重要的是避免重复执行已经完成的步骤。full mode 里还补强了 PostgreSQL 快照持久化，确保 tool_calls 和 approvals 的关系能正确恢复。

### 4.7 LangGraph 在这里起什么作用？

**话术：**

LangGraph 适合长运行、有状态、可中断、可恢复的 Agent workflow。项目里 `AGENT_RUN_ENGINE=langgraph` 时，可以用真实 LangGraph 编排创建 run、触发 approval interrupt，并用同一个 thread resume。

默认 `demo` engine 保留，是为了保证前端演示和测试稳定；LangGraph engine 用来展示更接近真实生产编排的能力。

### 4.8 Harness 和普通 function calling 的区别是什么？

**话术：**

普通 function calling 重点是“模型决定调用哪个函数”；Harness 重点是“函数调用是否被允许、是否需要审批、是否可恢复、是否可审计”。

所以 Harness 包含工具注册、风险等级、审批、状态机、审计日志、trace 和幂等控制。它更像企业 Agent 的执行治理层，而不是单纯的工具调用封装。

## 5. ACL、安全与审计

### 5.1 ACL 为什么必须在检索前生效？

**话术：**

如果先召回无权限内容，再在答案生成后过滤，敏感内容已经进入了 LLM 上下文，仍然可能泄露。企业场景里这是不可接受的。

所以项目要求 ACL 在检索前下推到 Milvus filter 和 Elasticsearch filter，只召回用户有权限看的 chunk；答案生成前再二次校验 citations，防止无权限 evidence 进入最终答案。

### 5.2 你如何防 prompt injection？

**话术：**

项目里有 prompt guard，对用户输入和文档内容中的可疑指令做检测，比如要求忽略系统规则、泄露 prompt、越权执行工具等。

更重要的是架构上做隔离：文档内容只作为 evidence，不作为系统指令；写入工具必须审批；工具权限由 registry 和 Harness 控制，而不是由文档或用户文本直接决定。

### 5.3 PII 脱敏做什么？

**话术：**

PII redactor 用来识别和脱敏手机号、身份证号、邮箱等敏感信息，避免敏感数据进入日志、trace 或用户不可见范围。

企业系统里不仅答案要安全，日志和可观测性数据也要安全，否则 trace 本身会变成泄露源。

### 5.4 audit log 和 trace 有什么区别？

**话术：**

trace 更偏技术排障，关注每个 span 的耗时、输入输出、错误和节点关系；audit log 更偏合规审计，关注谁在什么时候做了什么决策，尤其是审批、拒绝、工具执行等关键动作。

这个项目里两者都保留：trace 用于定位问题，audit log 用于追责和复盘。

### 5.5 企业 Agent 最大风险是什么？

**话术：**

我认为不是单纯“答错”，而是“错误执行有副作用动作”。比如错误创建工单、错误修改数据、错误发送消息。

所以项目把写入型工具审批作为硬约束，并结合 ACL、prompt injection 检测、rate limit、审计和 trace，限制 Agent 的行动边界。

## 6. 评测与可观测性

### 6.1 为什么 RAG/Agent 系统需要评测？

**话术：**

RAG 系统不能只靠主观感觉调参。检索、重排、答案生成和工具调用每一步都可能出问题，需要用指标定位。

项目里用 fake RAGAS 和 agent metrics 做 deterministic eval，关注 context precision、context recall、faithfulness、answer relevancy、tool call accuracy、approval correctness 等指标。

### 6.2 fake RAGAS 的意义是什么？

**话术：**

真实 RAGAS 可能依赖模型和网络，不适合作为单元测试基础。fake RAGAS 用确定性规则模拟评测结果，保证 CI 和本地测试稳定。

这符合项目的开发原则：先 deterministic fake 跑通闭环，再在 full mode 接真实外部能力。

### 6.3 trace 能帮你排查什么？

**话术：**

trace 可以定位一次 Agent Run 中哪一步慢、哪一步失败、哪次检索召回不相关、哪个工具经常被拒绝、哪个 prompt 版本导致答案忠实度下降。

fallback mode 用 log exporter，full mode 通过 OpenTelemetry OTLP HTTP 导出到 Phoenix，能够记录 Graph 节点级 span。

### 6.4 quality gate 包含哪些内容？

**话术：**

后端有 pytest 基线、quality gate、v1 final check、compileall；前端有 npm build 和 Playwright E2E。测试分层包括 unit、service、api、integration。

其中 unit/service/api 不依赖 Docker 和外部网络；integration 和 full E2E 需要 PostgreSQL、Redis、Milvus、Elasticsearch、MinIO 等外部服务启动。

## 7. 真实 AI 与 full mode

### 7.1 Qwen adapter 怎么接入？

**话术：**

项目接入了 Qwen chat completion、`text-embedding-v4` embedding 和 `qwen3-rerank` reranker adapter。有 `QWEN_API_KEY` 时 full mode 使用真实 AI；缺 key 时自动保持 deterministic fake。

这样既能展示真实模型能力，也不会让测试和 Demo 被云 API 阻塞。

### 7.2 为什么 embedding batch size 设置为 10？

**话术：**

这是为了适配 Qwen `text-embedding-v4` 单次最多 10 条输入的限制。IngestionPipeline 会根据 `EMBEDDING_BATCH_SIZE=10` 分批调用 embedding，避免一次传入过多文本导致 API 调用失败。

这个点体现的是 adapter 层要理解真实外部服务约束，而不是只写理想化接口。

### 7.3 PostgreSQL / Redis / Milvus / Elasticsearch / MinIO 分别做什么？

**话术：**

PostgreSQL 负责元数据、Agent Run、steps、tool calls、approvals 等持久化；Redis 用作 Celery broker、result backend 和 rate limit；Milvus 存向量索引；Elasticsearch 做 BM25 全文检索；MinIO 存原始文档 payload。

fallback mode 下这些能力分别由 in-memory store、local storage 和 fake adapter 替代。

### 7.4 full mode integration 被阻塞怎么解释？

**话术：**

当前 V1 closure 默认不把外部服务端口不可达视为失败，因为 V1 的核心是 fallback demo、API、前端控制台、Harness 审批恢复、RAG evidence/citations 和测试闭环。

如果要把 full mode 作为硬验收，可以运行 `scripts/v1_final_check.py --require-full`。这样 PostgreSQL、Redis、Milvus、Elasticsearch、MinIO 任一端口不可达都会返回非零退出码。

## 8. 前端控制台

### 8.1 前端为什么做控制台，而不是营销页？

**话术：**

这个项目的价值不是展示一个漂亮聊天框，而是展示 Agent 执行过程是否可控、可追溯。所以前端是操作型控制台，重点展示文档入库状态、Agent Run、evidence、plan/steps、approval card、tool result、trace 和 eval。

这也符合企业内部工具的设计目标：信息密度、状态可见性和操作闭环比营销式页面更重要。

### 8.2 前端如何接入 Agent Run？

**话术：**

前端通过 API 创建 Agent Run，通过 SSE 监听 run 事件，实时更新 step timeline、approval card、citations、tool result 和 trace。用户在 ApprovalCard 上执行 Approve/Edit/Reject 后，再调用 approval API 推动后端恢复执行。

Playwright E2E 覆盖了文档入库、Agent Run/SSE、Approve/Edit/Reject、citations 和 trace。

## 9. 标准 Demo 话术

**问题：如果让你现场演示，你怎么演示？**

**话术：**

我会先上传一份 HR 入职转正规章文档，让系统完成 ingestion，页面显示 ready 和 chunk 数量。

然后在 Agent Console 里提问“新员工入职到转正要办哪些事项？”。系统会先检索制度 evidence，并生成回答和 citations；接着生成办理 plan 和 checklist；当它准备调用 `create_mock_hr_ticket` 时，因为这是写入型工具，run 会进入 `awaiting_approval`，前端出现审批卡片。

我会点击 Approve，后端从同一个 run/thread 的 checkpoint 恢复，执行 mock ticket 工具，最后页面展示 ticket result、citations、step timeline 和 trace。这个 Demo 能完整体现 RAG 证据、Agent 计划、人工审批、工具执行和审计追踪。

## 10. 压迫式追问

### 10.1 你是不是只是堆技术名词？

**话术：**

不是。这个项目的主线很明确：企业 Agent 的可控执行。每个技术选择都服务这个主线。

RAG 是为了可信证据，citations 是为了可追溯，ACL 是为了权限隔离，approval 是为了控制副作用工具，checkpoint/resume 是为了长流程恢复，trace/eval 是为了排障和质量闭环。不是为了堆栈而堆栈。

### 10.2 为什么不用现成 RAG 框架直接做？

**话术：**

现成框架可以快速搭建检索问答，但这个项目重点不是单纯回答，而是企业 Agent 的执行治理。审批、权限下推、工具风险等级、审计、状态恢复和可测试 fake 这些，需要明确的领域边界和状态管理。

所以我参考框架能力，但核心 Harness 和服务边界是自研设计的。

### 10.3 你怎么证明审批前工具没有执行？

**话术：**

从设计和测试两方面证明。设计上，`requires_approval=true` 的工具在 Tool Executor 中不会直接调用工具实现，而是创建 approval request 和 tool call preview，并把 run 切到 `awaiting_approval`。

测试上，service/api/E2E 都覆盖了审批前只出现 approval card，不产生 tool result；Approve 后才恢复执行并记录结果。

### 10.4 你怎么证明 ACL 没有泄露？

**话术：**

首先，ACL 在检索前生效，不是生成后过滤。Milvus 和 Elasticsearch 查询都会带权限过滤条件。

其次，EvidenceBuilder 和 AnswerService 在生成前会二次校验 citations，确保最终答案引用的 evidence 仍在用户权限范围内。

最后，安全测试覆盖了权限过滤和无权限内容排除场景。

### 10.5 如果模型胡编 citation 怎么办？

**话术：**

系统不让模型自由生成 citation。citation 由后端基于 EvidenceBundle 构造，包含来源文档、章节、页码或段落、分数等结构化字段。

模型负责根据 evidence 组织自然语言答案，citation 由 citation builder 和 answer service 控制。这样可以降低模型编造来源的风险。

### 10.6 如果 Qwen API 或外部服务不可用怎么办？

**话术：**

项目默认保留 fallback mode。缺少 API key 或外部中间件不可用时，核心 Demo 和单元测试仍然可以通过 deterministic fake 跑通。

full mode 用于真实集成验证；fallback mode 用于开发、测试和演示稳定性。这是项目刻意设计的工程取舍。

### 10.7 如果 Celery 任务重复投递怎么办？

**话术：**

写入型和入库型流程都需要幂等思路。入库任务有 task 状态和 document/chunk 索引记录，重试前会清理旧向量索引，避免重复 chunk 残留。

对于工具执行，tool call 和 approval 都绑定 run id，并记录执行状态，避免审批恢复后重复执行同一个写入动作。

### 10.8 如果让你继续做 V2，你会做什么？

**话术：**

我会优先做三个方向。

第一是 GraphRAG / LightRAG，用来处理跨文档、多实体、多跳关系问题。

第二是 MCP Server，把企业知识库和 Agent Harness 能力标准化暴露给其他 Agent 或办公系统。

第三是真实 HR 系统 adapter，但仍然保持写入型工具必须审批，并补充更完整的 RBAC、审计和幂等保障。

## 11. 最推荐背诵的 6 个短答案

### 11.1 项目一句话

EnterpriseMind 是一个把 RAG 可信证据层和 Agent Harness 执行治理层结合起来的企业知识任务智能体平台，V1 聚焦 HR 制度问答和审批后模拟工单执行。

### 11.2 最大亮点

最大亮点不是“能回答”，而是“可控地执行”：答案有 citations，检索有 ACL，写入工具必须审批，审批后能 checkpoint/resume，整个过程有 audit 和 trace。

### 11.3 技术主线

技术主线是先用 deterministic fake 跑通 pure Python/in-memory 主链路，再通过 adapter 替换成 PostgreSQL、Redis、Milvus、Elasticsearch、MinIO、Qwen、Celery 和 Phoenix。

### 11.4 RAG 可信性

可信性来自 EvidenceBundle、citation builder、低置信度拒答、ACL 检索前过滤和答案生成前二次校验，不依赖模型自己保证不幻觉。

### 11.5 Agent 安全性

安全性来自 Tool Registry 的风险分级、写入型工具强制 approval、审批前只生成 preview 不执行、审批后同 run/thread 恢复，以及全流程 audit log。

### 11.6 工程化体现

工程化体现在分层清晰、外部依赖 adapter/fake、测试分层、质量门禁、SSE 前端闭环、full/fallback mode、真实 AI adapter 和可观测 trace。
